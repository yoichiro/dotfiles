description: Mines the user's archived Claude Code conversation history (the "tsukune" Obsidian vault at ~/Desktop/obsidian/tsukune/<developer>/*.md) to discover architecturally significant decisions made during a project's real development, and writes/maintains them as lightweight Architecture Decision Records (ADRs) in the project's docs/arch (or a user-chosen) directory. Use this whenever the user asks to create ADRs, write architecture decision records, document why past technical decisions were made, build a decision log from chat history, or asks things like "ADRを作成して", "アーキテクチャ意思決定を記録して", "過去の設計判断をまとめて", "why did we do X" about this project's history — even if they never say the word "ADR". Also use this to refresh/update existing ADRs after more development has happened: it re-mines the conversation history, checks each existing ADR for contradictions against what actually happened later, and marks superseded decisions instead of silently rewriting history. Do not use this for writing a single one-off design doc for a not-yet-built feature (see design-doc-writer for that) — this skill is specifically about reconstructing decisions that were already made and discussed in past sessions.

# ADR from history

このスキルは、洋一郎さんがClaude Codeと交わした過去の会話（`tsukune`によってアーカイブされたセッションログ）から、対象プロジェクトにおける「アーキテクチャ上重要な意思決定」を発掘し、軽量なMarkdown形式のADR（Architecture Decision Record）としてファイル化・保守する。

会話ログは1セッション1ファイルのMarkdownで、`~/Desktop/obsidian/tsukune/<developer-email>/`配下に日付プレフィックス付きファイル名（`YYYY-MM-DD-<session_id>.md`）で置かれており、各ファイルの先頭にYAML frontmatter（`session_id`, `developer`, `started_at`, `project.path`など）が付与されている。このディレクトリ構成が存在しない環境（初回、あるいは別マシン）では、ユーザーに実際のパスを尋ねること。

## 全体の流れ

1. ADRの出力先ディレクトリを確認する
2. 対象プロジェクトの会話ログを特定し、重複を除去する
3. 会話ログの中からアーキテクチャ上重要な意思決定を発掘する（規模に応じて並列サブエージェントに分担させる）
4. 発掘した意思決定を、既存のADRと突き合わせて整理する（新規作成／更新／変更なし／過去のADRの置き換え）
5. ADRファイルを規約に沿って書く（または更新する）
6. 結果をユーザーに要約報告する

以下、各ステップの詳細。

## 1. 出力先ディレクトリの確認

作業を始める前に、必ずユーザーに出力先を確認する。`docs/arch`（プロジェクトルートからの相対パス）を初期値として提示し、ユーザーがそれを了承すればそれを採用、明示的に別のパスが指定されればそちらを採用する。既にこのプロジェクトでADRを書いたことがあり出力先が明らかな場合（例えば直近の会話で使ったディレクトリがある場合）は、それを初期値の候補として添えてよい。

このステップは省略しない。ユーザーに聞かずに`docs/arch`を決め打ちしない。

## 2. 対象プロジェクトの会話ログの特定と重複排除

対象プロジェクトのルート（`git rev-parse --show-toplevel`、Gitリポジトリでなければ現在の作業ディレクトリ）の絶対パスを求める。

会話ログは`~/Desktop/obsidian/tsukune/*/*.md`（developerのメールアドレス名のサブディレクトリが複数存在しうる）に置かれている。それぞれのファイルの中身をキーワードで検索するのではなく、frontmatterの`project:`ブロック内の`path:`が対象プロジェクトの絶対パスと**完全一致**するものだけを対象にする。ファイル内容にプロジェクト名の文字列がたまたま含まれているだけのファイル（無関係な会話で言及されただけ）を拾わないよう、必ずfrontmatterで判定すること。

```bash
grep -l "path: <project_root>$" ~/Desktop/obsidian/tsukune/*/*.md
```

同一の会話セッションが、日をまたいでresumeされるたびに別の日付プレフィックスで再エクスポートされ、複数ファイルとして存在することがある（同じ`session_id`が異なる日付のファイル名で重複する）。これらは同じ会話の異なる時点のスナップショットなので、`session_id`ごとに最も新しい日付のファイルだけを残し、それ以外は読み込み対象から除外する。

## 3. アーキテクチャ上重要な意思決定の発掘

対象ファイルは1つあたり非常に大きくなることがある（数十万トークン規模）。**ファイルを先頭から丸ごと読んではいけない。** また、ファイルの中身は実際の対話だけでなく、ツール呼び出しの生JSONが大量に混在している。効率よく探すには：

- `### user` / `### assistant` という見出しが実際の対話ターンの区切りであり、それ以外の部分（生JSON）は基本的に読み飛ばしてよい。
- 意思決定が語られている箇所は、次のようなキーワードの近くに現れやすい: 「設計」「方針」「アーキテクチャ」「採用」「却下」「ではなく」「にする」「変更」「移行」「分離」「責務」「トレードオフ」「instead of」「decided」「let's use」「should we」「architecture」「approach」「trade-off」。
- `grep`でこれらのキーワードやセクション見出しの行番号を特定し、その周辺だけを`Read`の`offset`/`limit`で読む。

対象ファイル数が多い場合（目安として20ファイルを超える場合）は、日付や件数で均等にグループ分けし、グループごとに`Agent`ツールで並列にサブエージェントを立てて調査させる。1グループあたり15〜25ファイル程度が扱いやすい。ファイル数が少ない場合（目安20ファイル以下）は、無理に並列化せず自分自身で直接`grep`/`Read`して調査すること。`Workflow`ツールは、ユーザーが明示的にワークフロー実行を求めない限り使わない。

**自分自身がすでにサブエージェント（他のエージェントから呼び出された存在）として動いている場合は、原則としてさらに下位にサブエージェントを委任しない。** 実際の運用では、委任先の完了を待たずに「他のエージェントの完了を待っています」という未完了のステータスメッセージだけで自分のターンを終えてしまい、その後何度催促しても同じことを繰り返す、という失敗が繰り返し観測されている。これは委任の階層が一段深くなるほど起こりやすい。対象ファイル数が少ない〜中程度（数十ファイル程度まで）であれば、多少時間がかかっても自分で`grep`/`Read`を直接叩いて調査したほうが、結果的に速く確実に完了する。

やむを得ず並列委任する場合は、各調査（サブ）エージェントには次を明確に指示すること。

- 対象は「アーキテクチャ上重要な意思決定」（システム構成、技術選定、データフロー、API設計、クライアント/サーバーの責務分担、永続化戦略、セキュリティ境界などについて、複数の選択肢を比較したうえで下された判断）に限る。単純なバグ修正、文言・CSSの微調整、そして「diffに対する事後のセキュリティレビューのみで実際の設計対話を含まないセッション」は対象外とする。
- 発見した意思決定ごとに、日付・ファイル名・タイトル・1〜2文の説明（決定内容と根拠）を返すこと。
- 該当がなければ、そのファイル・グループについては黙ってスキップしてよい。無理に何かを報告させない。
- 自分がさらに下位のサブエージェントに委任してはならないこと、必ず自分自身の調査結果を最終回答として返すことを明示する。

**運用上の注意**: サブエージェントが実際の調査結果ではなく「他のエージェントの完了を待っています」のような要領を得ない応答を返すことがある。この場合、`SendMessage`でそのエージェントに再度「あなたは単独で作業しており、他のエージェントを待つ必要はない。委任は諦めて自分自身で直接調査し、今すぐ最終回答を出力せよ」と明確に伝えて再実行させること。同じ応答が繰り返される場合は、委任自体を諦めて自分（呼び出し元）が直接調査を引き継ぐ。

全サブエージェントの結果が揃ったら、重複を除いて時系列順の意思決定候補リストにまとめる。

## 4. 既存ADRとの突き合わせ

出力先ディレクトリに既存のADRファイル（`adr-XXXX-*.md`）があれば、そのタイトルとDecisionセクションを読み、発掘した意思決定候補それぞれについて次のいずれに該当するかを判断する。

| ケース | 対応 |
|---|---|
| 同じ意思決定を扱う既存ADRがあり、内容に矛盾がない | 何もしない（無意味な書き換えをしない） |
| 同じ意思決定を扱う既存ADRがあるが、新たに判明した情報によりContext／Decision／Consequencesの記述が不正確・不足だとわかった | そのADRファイルを直接更新する（Statusは変更しない） |
| どの既存ADRも扱っていない、真に新規の意思決定である | 新しいADRファイルを作成する |
| 新たに発掘した意思決定が、**別の**既存ADRが記録した決定を覆す・置き換えるものである（プロジェクトが方針転換した） | 古いADRのContext／Decision／Consequencesの本文はそのまま変更せず、**Statusフィールドのみ**を「非推奨（Deprecated）」または「置き換え済み（Superseded by ADR N）」に変更し、変更理由と新しいADRへのポインタを添える。新しい決定自体は、通常どおり新規ADRとして作成する。 |

意味的に変化がなければ更新しない、という判断を軽視しないこと。既存ADRへの毎回の細かい言い回し変更は、後から読む人にとってのノイズになる。

## 5. ADRファイルの規約

以下の構成・記法は固定であり、独自に変えないこと。

**ファイル名**: `adr-XXXX-kebab-case-english-slug.md`（`XXXX`は出力先ディレクトリ内の既存ADRの最大番号を0埋め4桁でインクリメントしたもの。ディレクトリが空・未作成なら`0001`から開始）。日本語の内容であっても、ファイル名のスラッグは検索・参照のしやすさを優先して短い英語にする。

**セクション構成**（この順・見出しレベルで固定）:

```
# ADR N: 短い名詞句のタイトル

## Context

## Decision

## Status

## Consequences
```

**各セクションの書き方**:

- **Context**: 技術的・政治的・社会的・プロジェクト固有の事情など、意思決定に影響した力学を、価値判断を交えず客観的な事実として記述する。複数の事情が対立・緊張関係にあった場合は、その旨を明記する。
- **Decision**: 「私たちは〜します」のように、完全な文章・能動態で明確に書く。何を選び、何を選ばなかったか（比較検討した代替案とその却下理由）が分かるように書く。
- **Status**: 洋一郎さんの単独開発であるため「提案中（proposed）」は使わない。決定された時点で「承認済み（Accepted）」とする。後続の意思決定によって覆された場合のみ、「非推奨（Deprecated）」または「置き換え済み（Superseded by ADR N）」に変更する。
- **Consequences**: 決定後に実際に生じた結果を、良い面だけでなく悪い面・中立的な面も含めて率直に書く。会話ログの中でセキュリティレビュー等により指摘されたが未対応のまま残っているリスクがあれば、ここに記載する。ここに書いた内容は、将来の別のADRの「Context」になりうる。

**文体**: 全文「です・ます」調。箇条書きは視覚的な整理のためだけに使い、文章を不完全な断片にする言い訳にしない。

**相互参照**: 関連する既存ADRへの言及は、ファイル名（拡張子なし）を使って`[[adr-000X-slug]]`のようにWikiリンク形式で埋め込む。

## 6. 結果の報告

作業の最後に、次を一覧できる形でユーザーに報告する。

- 新規作成したADR（番号・タイトル）
- 内容を更新した既存ADR（番号・タイトル・更新理由）
- Statusを変更した既存ADR（番号・タイトル・新しいStatus・原因となった新規ADRへのポインタ）
- 変更なしと判断した既存ADR（件数のみで十分。個別に列挙する必要はない）

## 実装上のヒント

- スクラッチ用の一時ファイルを`zsh`のヒアドキュメントやリダイレクトで書く際、`noclobber`設定により`>`が既存ファイルへの上書きを拒否してエラーになることがある。事前に`rm -f`するか、`set +o noclobber`してから書き込むこと。
- 会話ログのfrontmatterは`session_id:`, `started_at:`, `project:` → `path:`のようにネストしている。`grep`だけで完結させず、必要に応じて該当行の周辺を読んで構造を確認すること。
- ADRファイルを書いている途中で「自分が作っていないはずのファイルが増えている／書き換わっている」ように見えることがある。ほとんどの場合、これは他プロセスの干渉ではなく、自分自身が少し前のターンで書いた内容を忘れている（あるいは見落としている）だけである。`rm -f`で削除してから書き直す、といった対応は絶対に避け、まず現在のファイル内容を素直に読み直し、それを出発点として編集（in-place）で修正すること。本当に自分の意図しない内容であっても、削除より先に、まずユーザーに報告して判断を仰ぐ方が安全である。
- ADRの構成（Context/Decision/Status/Consequencesの4セクション、この順序）は固定であり、途中で「## Update」のような規約にないセクションを追加しない。書き終えたら、規定の4セクションだけになっているかを最後に見直すこと。
